01 — THE QUESTION

How do you make a hydrofoil move precisely enough to become an experiment?

Marine-energy experiments depend on repeatable physical motion. The hydrofoil needed to move to defined angular positions, return to a known reference, oscillate between positions, and hold position using an electromagnetic brake.

What began as a practical hardware problem gradually became a systems-engineering problem: how do mechanical hardware, electronics, embedded software, communication, and supervisory software interact as one system?

04 — EMBEDDED CONTROL

The first system was deliberately low-level.

The initial implementation focused on understanding the actuator itself. Arduino firmware directly generated motor pulses, calculated target positions, and controlled the brake.

// Representative excerpt from the original
// low-level actuator implementation

const int STEP_PIN = 4;
const int DIR_PIN = 3;
const int BRAKE_PIN = 7;

const long PULSES_PER_REV = 12500;

void moveToAngle(float targetAngle) {

    long targetPulses =
        targetAngle / 360.0
        * PULSES_PER_REV;

    // Set direction and generate STEP pulses
    digitalWrite(DIR_PIN, direction);

    for (long i = 0;
         i < abs(targetPulses);
         i++) {

        digitalWrite(STEP_PIN, HIGH);
        delayMicroseconds(stepDelay);
        digitalWrite(STEP_PIN, LOW);
        delayMicroseconds(stepDelay);
    }
}

05 — DEBUGGING

The motor taught me that code can be correct and still be wrong.

INTERFACE FAILURE

The microstepping assumption did not match the physical configuration.

The firmware contained an assumption about pulses per revolution that did not initially match the motor driver's actual configuration. The result was a mismatch between commanded and observed angular movement.

Rather than treating the behavior as a mysterious software error, the debugging process required tracing the assumption across the software and hardware boundary.

ENGINEERING LESSON A control system is only as accurate as the assumptions connecting its physical and software layers.

06 — VALIDATION

Could it actually return where I told it to?

After establishing basic positioning and oscillation, the system was tested through repeated incremental movements to investigate angular repeatability.

The system was moved approximately 90°, then commanded through approximately 3° increments 30 times, returning toward the original position.

SCOPE BOUNDARY Full hydrodynamic characterization was outside Yatharth's testing scope.

07 — SYSTEM ARCHITECTURE

The motor worked. Then I realized the architecture didn't scale.

Direct Arduino control was useful for one actuator. A larger experimental facility would eventually require multiple actuators, controllers, sensors, stations, communication channels, and centralized monitoring.

13 — ENGINEERING LESSONS

What the system taught me.

01

Physical assumptions matter.

A software constant is meaningless if it does not match the physical configuration it represents.

02

Debugging is part of design.

The microstepping mismatch became a lesson about validating interfaces between abstraction layers.

03

Systems are more than components.

A motor, driver, controller, communication protocol, and supervisory layer must work together.

04

Architecture determines scalability.

A solution that works for one actuator can become a bottleneck when the system grows.

14 — REFLECTION

I started with a motor I didn't understand.

I began this project knowing very little about stepper motors, embedded control, or supervisory systems. I finished with a working hydrofoil actuation subsystem and a deeper understanding of how mechanical hardware, electronics, software, and control architecture interact.

The most important result was not simply that the hydrofoil moved. It was learning how to enter an unfamiliar engineering problem, isolate what I didn't understand, test assumptions, recover from failures, and gradually build a system in which the pieces could work together.

The shaft moved first. The systems thinking came after.
